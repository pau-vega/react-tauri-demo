  <how-to-verify>
    CHECK 1 — Cold-start empty state (or populated from prior runs) — TODO-04 and PERS-02:

    Look at the screen. The "Tauri Todo" heading is visible at the top. Below it is a text input with placeholder "Add a todo..." and an "Add" button to the right.
    - If you have NEVER run this app before (fresh install, no prior todos): you should see "No todos yet / Add your first todo above" centered below the input after a brief Loading... message.
    - If you have run this app before and added todos (e.g., from a prior verification session): you should see those existing todos in a list below the input.
    - The "Loading..." message should appear only briefly (well under 1 second) and then disappear. It must NOT be stuck on screen.

    Expected outcome: either empty-state panel OR a list of previously-added todos. Either is acceptable for this check. If you see "Loading..." for more than 5 seconds, REPORT this.

    CHECK 2 — Add a todo — TODO-01:

    Tap the text input. The on-screen keyboard should appear. Type: "Buy milk"
    Tap the "Add" button (or press the Enter/Return key on the keyboard — both should work).

    Expected outcome:
    - The input clears immediately after tapping Add
    - A new row appears in the list below with the text "Buy milk"
    - The row has a circular button on the left (outline, white fill)
    - The row has an "×" icon button on the right (gray)
    - The text "Buy milk" is between them, normal-weight black

    If the input does not clear, or the todo does not appear, or the Add button does nothing, REPORT this.

    CHECK 3 — Add at least 2 more todos — TODO-01 with stacking:

    Add two more todos (e.g., "Walk dog", "Read book"). Each should appear stacked vertically below "Buy milk" with small gaps between rows. All three rows should be visible at once.

    Expected outcome: 3 rows visible, in the order added (top = oldest, bottom = newest).

    If rows overlap, stack incorrectly, disappear after adding, or if only the newest one shows, REPORT this.

    CHECK 4 — Toggle completion — TODO-02:

    Tap the circular button on the left of "Walk dog".

    Expected outcome:
    - The circle turns solid blue
    - A white checkmark (✓) appears inside the circle
    - The text "Walk dog" gets a strikethrough line and the color dims to light gray
    - The row stays in place (does not move, reorder, or disappear)

    Tap the circle AGAIN on "Walk dog".

    Expected outcome:
    - The circle returns to outline-only (white fill, gray border)
    - The checkmark disappears
    - The text returns to solid black with no strikethrough

    If the visual change does not happen, if the whole row disappears, or if a different row changes instead, REPORT this.

    CHECK 5 — Delete a todo — TODO-03:

    Toggle "Buy milk" to completed state (tap its circle once). Then tap the "×" button on the right of "Buy milk".

    Expected outcome:
    - The "Buy milk" row disappears immediately from the list
    - No confirmation dialog or prompt appears (D-14: immediate delete by design)
    - The remaining todos ("Walk dog", "Read book") shift up to fill the gap
    - There is no error banner or visual glitch

    If a confirmation dialog appears, if the row stays visible, or if the wrong row is deleted, REPORT this.

    CHECK 6 — Empty state after deleting all — TODO-04:

    Delete the remaining todos one at a time ("Walk dog", then "Read book") by tapping each X button.

    Expected outcome: after deleting the last remaining todo, the list area shows "No todos yet / Add your first todo above" centered below the input.

    If the empty-state message does not appear after the last delete (e.g., a blank area remains, or a stale row ghost persists), REPORT this.

    CHECK 7 — Persistence across app restart — PERS-02 (the critical one):

    Add 2 fresh todos (e.g., "Call dentist", "Pay rent"). Verify both appear.

    Now fully close the app:
    - Tap the Android recent-apps button (usually the square or three-line icon at the bottom of the screen)
    - Swipe the Tauri Todo app card up and off the screen (or tap the X on the card, depending on your Android version)
    - Confirm the app is gone from the recents list

    Reopen the app:
    - Find it in the app drawer and tap to launch (or if using `tauri android dev`, the dev launcher script will auto-reopen on code change — in that case, tap the app icon from the home screen/drawer directly instead)

    Expected outcome:
    - After the brief "Loading..." flash, BOTH "Call dentist" and "Pay rent" should be visible in the list
    - Their order must match what it was before closing
    - Their completed state (if you toggled any) must match what it was before closing

    If the list is empty after restart, if only some todos persist, or if the completed state is lost, REPORT this. PERS-02 is the most important requirement in this phase — a failure here blocks sign-off.

    - What did you expect?
    - What actually happened?
    - Screenshot if possible (attach any image of the error or glitch)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User touch input to WebView | Android hardware events routed to Chromium WebView; handled by React onClick and onSubmit |
| WebView to Tauri Rust shell | IPC via store plugin; same as Plans 01 and 02 (no new boundaries introduced here) |
| Android OS lifecycle to app | OS can kill the app process at any time (low memory, user swipe-to-close); app must cold-start with correct state |

This plan introduces no new code, so no new trust boundaries. It validates the behavior of boundaries already established in Plans 01 and 02.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-13 | Tampering | Device in a non-trusted state (rooted, sideloaded app, debug mode) | accept | Phase 2 is a user verification step; the tester is the developer running their own local build. If the device is rooted, that is out of scope for this local todo experiment. |
| T-02-14 | Information disclosure | Error output in adb logcat during verification | accept | adb logcat output is visible only to the developer running this verification; no PII, no secrets in any error path (the app has none). |
| T-02-15 | Denial of service | First-compile 10-30min blocking the checkpoint | mitigate | STATE.md pre-warns about first compile duration. Task 1 Step 3 notes "10-30 minutes" explicitly so the user does not misinterpret as a hang. |
| T-02-16 | Elevation of privilege | adb install leaves the app on device after verification | accept | Developer can uninstall via Settings > Apps or adb uninstall at any time. No persistent privilege granted beyond the app's own sandbox. |
| T-02-17 | Spoofing | N/A | accept | No authentication. |
| T-02-18 | Repudiation | N/A | accept | User is sole actor; audit log unnecessary. |
