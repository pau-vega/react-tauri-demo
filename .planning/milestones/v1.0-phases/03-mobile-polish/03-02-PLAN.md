- type: auto

action:

Overwrite apps/tauri-todo/src-tauri/src/lib.rs with this exact content:

```
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_store::Builder::new().build())
        .setup(|app| {
            #[cfg(mobile)]
            app.handle().plugin(tauri_plugin_haptics::init())?;
            Ok(())
        })
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

Critical constraints (Pitfall 1):
- Store plugin stays at Builder root (`.plugin(tauri_plugin_store::Builder::new().build())`) — it's cross-platform, the existing pattern works.
- Haptics MUST be inside `.setup(|app| { ... })` with `#[cfg(mobile)]` on the line immediately above `app.handle().plugin(tauri_plugin_haptics::init())?;`. On desktop builds, the `#[cfg(mobile)]` line vanishes and the closure returns Ok(()).
- The `?` operator on `app.handle().plugin(...)?` propagates errors out of the closure.
- The closure returns `Ok(())` unconditionally (typed as `Result<(), Box<dyn Error>>` by Tauri's setup signature).
- Do NOT wrap store registration inside .setup() — keep it at root where it is.
- Do NOT add `use` statements for tauri_plugin_haptics — the `::init()` qualified path works without an import and matches the pattern in the official plugin docs.

4-space indentation (matches existing file); no trailing whitespace; preserve `#[cfg_attr(mobile, tauri::mobile_entry_point)]` attribute verbatim.

## Threat Model

### Trust Boundaries

| Boundary | Description |
|----------|-------------|
| JS WebView → Tauri Rust IPC | Plugin calls cross from untrusted WebView JS into the native Rust host via Tauri's IPC. Capability file gates which commands are callable. |
| Rust → Android OS VibrationEffect API | Native crate invokes OS-level haptic APIs; OS mediates hardware access. |

### STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03 | E (Elevation of Privilege) | Capability file granting broader than needed | mitigate | Grant only three specific `haptics:allow-*` permissions (D-09). Do NOT use `haptics:default`. Acceptance criteria test for the absence of `haptics:default` and `haptics:allow-vibrate`. |
| T-03-04 | E (Elevation of Privilege) | Mobile-only crate leaking into desktop attack surface | mitigate | Cargo target-cfg section `[target.'cfg(any(target_os = "android", target_os = "ios"))'.dependencies]` ensures the crate never links on desktop hosts. Pitfall 1 enforcement: lib.rs uses `#[cfg(mobile)]` inside `.setup()` to guard the plugin init line. |
| T-03-05 | T (Tampering / QA gap) | Silent plugin install bug (typo, omitted capability string) | mitigate | Plan 01's capabilities.test.ts asserts all three literal permission strings are present; runs on every `pnpm test`. |
| T-03-06 | I (Information Disclosure) | User todo data leaking via haptic IPC | accept | Haptic plugin calls (to be wired in Plan 04) pass only literal strings ("medium", "warning"). No todo text, IDs, or user data crosses the haptics IPC boundary. |
| T-03-07 | D (Denial of Service) | Capability file corruption breaks Tauri runtime load | mitigate | JSON validity checked in acceptance criteria; existing `core:default` and `store:default` preserved so app still boots if a Phase 3 bug somehow drops them. |

Phase 1 reference: the capability model (mobile.json with `core:default` + `store:default`) is the baseline. This plan extends — does not alter — that boundary.
