# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3: Mobile Polish. Generated by gsd-ui-researcher from upstream artifacts (REQUIREMENTS UX-01..04, CONTEXT D-01..D-19, RESEARCH Patterns 1-4). Verified by gsd-ui-checker.

This phase is **polish-only** over the Phase 2 todo app. No new surfaces, no new copy, no new components — touch-target sizing, haptic feedback, and safe-area insets are the full scope. All tokens below describe the *existing* Phase 2 visual contract plus the Phase 3 deltas, so downstream agents implement against a complete picture.

## Spacing Scale

Declared values (all multiples of 4 — matches Tailwind's default `1 = 4px` scale already in use):

| Token | Value | Tailwind | Usage in this phase |
|-------|-------|----------|---------------------|
| xs | 4px | `gap-1` / `p-1` | not used in this phase |
| sm | 8px | `gap-2` / `p-2` | `TodoInput` gap between input and button; `TodoList` gap between items |
| md | 12px | `gap-3` / `px-3 py-3` | `TodoItem` row padding (D-06 — stays as-is) and row `gap-3` between toggle/text/delete |
| lg | 16px | `gap-4` / `px-4` | `<main>` horizontal padding (`px-4`) — keeps content off screen edges |
| xl | 24px | `gap-6` | `TodoApp` vertical rhythm between title / input / list (`flex-col gap-6`) |
| 2xl | 32px | `py-8` / `2rem` | Current `<main>` vertical padding floor; becomes `max(2rem, env(safe-area-inset-*))` per D-15/D-16 |
| 3xl | 48px | `py-12` | Empty/loading/error state vertical breathing room on `TodoList` placeholders |

### Touch target floor (44px) — phase-specific

**44px is the interactive-control floor, not a spacing token.** Apple HIG and Android Material converge on this minimum. Tailwind's default scale resolves `11` to `2.75rem = 44px` at the standard 16px root font size, so the contract uses `h-11` / `w-11 h-11` literally.

| Control | Before | After | Tailwind | Source |
|---------|--------|-------|----------|--------|
| `TodoInput` input | 40px | **44px** | `h-11` | D-02 |
| `TodoInput` Add button | 40px | **44px** | `h-11` | D-03 |
| `TodoItem` toggle (complete/incomplete) | 24px | **44px** | `w-11 h-11` | D-04 |
| `TodoItem` delete button | 32px | **44px** | `w-11 h-11` | D-05 |

**Hit area = visible area** (D-01). No hidden-padding / invisible-absolute hit-area tricks. The control you see is the control you tap.

### Exceptions

- `TodoItem` row padding (`px-3 py-3`) stays at 12px **despite** the 44px controls now living inside it (D-06). Rows will look slightly taller because of the controls; that is intentional breathing room, not a separate spacing change.
- Inner glyphs inside the 44px controls (`✓` inside toggle, `×` inside delete) are sized by text size class, not the container token — the container is the hit target, the glyph is pure visual. Exact glyph sizes are Claude's discretion per CONTEXT (post "Claude's Discretion" list).

### Safe-area inset padding on `<main>` (D-15, D-16, Pitfall 5)

Top and bottom padding of `<main>` becomes a `max()` of the current 2rem floor and the device's reported safe-area inset. Left/right insets not needed — Android typically has no horizontal notch and `px-4` already clears screen edges.

| Property | Value |
|----------|-------|
| `padding-top` | `max(2rem, env(safe-area-inset-top))` — Tailwind: `pt-[max(2rem,env(safe-area-inset-top))]` |
| `padding-bottom` | `max(2rem, env(safe-area-inset-bottom))` — Tailwind: `pb-[max(2rem,env(safe-area-inset-bottom))]` |
| `padding-left` | `1rem` — unchanged `px-4` |
| `padding-right` | `1rem` — unchanged `px-4` |

Why `max()`: Android WebViews without a notch return `0px` for `env(safe-area-inset-*)`. A raw `pt-[env(...)]` would collapse the current 2rem floor and push the title against the status bar on older devices (Pitfall 5).

## Typography

Three sizes, two weights. Matches what's already in the Phase 2 components — no size or weight bump in this phase (that was deferred per CONTEXT "Deferred Ideas").

| Role | Size | Weight | Line Height | Tailwind | Appears on |
|------|------|--------|-------------|----------|-----------|
| Display / Page title | 20px | 600 (semibold) | 1.2 (default for `text-xl`) | `text-xl font-semibold` | `TodoApp` `<h1>` "Tauri Todo" |
| Body | 16px | 400 (normal) | 1.5 (default for `text-base`) | `text-base` | `TodoInput` input, `TodoItem` text, "No todos yet" empty heading |
| Caption / Helper | 14px | 400 (normal) | 1.5 (default for `text-sm`) | `text-sm` | "Add your first todo above", "Loading...", error line |
| Button label | 14px | 400 (normal) | 1.5 | `text-sm font-normal` | `TodoInput` Add button |

**Inline decoration:**
- Completed todo text: `line-through` + `text-gray-400` — single-use, no separate token needed.
- Delete glyph `×`: `text-xl leading-none` — visual-only scaling inside the 44px container (Claude's discretion per CONTEXT).
- Toggle checkmark `✓`: `text-white text-xs` currently. After D-04 grows container to 44px, glyph may scale up for visual balance (Claude's discretion) — recommended `text-sm` or `text-base`, keep `text-white` for contrast on the filled-blue completed state.

**Weight count: 2** (normal 400, semibold 600). No italic, no bold beyond semibold.
**Size count: 3** (xl/20, base/16, sm/14) — under the 3-4 cap from the ui-researcher success criteria.

## Color

Light-only scheme per Phase 1 D-27 (dark mode explicitly deferred). Values are Tailwind v4 palette references already baked into the Phase 2 components — this phase **does not change any color**; it is enumerated here so the checker and auditor can validate 60/30/10 adherence.

| Role | Value | Tailwind | Usage |
|------|-------|----------|-------|
| Dominant (60%) | `#ffffff` | `bg-white` | App background (`<main>`), row background, input field background |
| Secondary (30%) | `#f3f4f6` (gray-100) + `#e5e7eb` (gray-200) | `border-gray-200`, `border-gray-300` | Row borders, input border, incomplete-toggle outline ring |
| Accent (10%) | `#1d4ed8` (blue-700) | `bg-blue-700`, `text-blue-700`, `focus:ring-blue-700`, `border-blue-700` | See reserved-for list below |
| Destructive | `#dc2626` (red-600) | `text-red-600`, `active:text-red-600` | Error state copy + delete-button pressed state only |

### Accent reserved for

Explicit list — **accent is not applied to every interactive element**. The checker validates this list literally.

1. `TodoInput` Add button primary surface (`bg-blue-700 text-white`)
2. `TodoInput` input focus ring (`focus:ring-blue-700`)
3. `TodoItem` toggle **completed** state fill + border (`bg-blue-700 border-2 border-blue-700`)

**Accent is NOT applied to:**
- `TodoItem` toggle incomplete state (stays gray-bordered white — a neutral resting state)
- `TodoItem` row backgrounds (stays white)
- `TodoItem` text (stays gray-900 for incomplete, gray-400 for completed)
- `TodoItem` delete button (stays gray-400, with red-600 only on active press)
- Any heading, label, or helper text

### Text tones

| Role | Value | Tailwind |
|------|-------|----------|
| Primary text | `#111827` (gray-900) | `text-gray-900` |
| Secondary text / placeholder | `#6b7280` (gray-500) | `text-gray-500` |
| Disabled / completed-through | `#9ca3af` (gray-400) | `text-gray-400` |
| Inverse text (on accent) | `#ffffff` | `text-white` |
| Destructive text (error copy + delete press) | `#dc2626` | `text-red-600` |

### Destructive palette — how it reads to the user

Destructive color appears in exactly two places:
1. **Error state copy** in `TodoList` when `state.status === "error"`.
2. **Delete-button press feedback** — `active:text-red-600` on the `×` glyph. The red flash is the primary press confirmation for destruction; haptic `notificationFeedback('warning')` is the secondary (tactile) confirmation per D-12.

No red fills, no red borders on idle states. Destruction is signaled only while the user is actively engaging it, keeping the default palette calm.

## Interaction Contract (Phase 3 addition)

No hover states anywhere (D-17 / UX-02 — already verified absent). All press feedback is touch-first.

### Press feedback pattern

Continue the Phase 2 established pattern: `active:opacity-90` on every interactive control. Already applied to Add button, toggle, and delete — no changes needed for the touch-target pass.

### Haptic feedback (D-07..D-14, Patterns 2 & 3)

Haptics pair with each of the three primary CRUD interactions. Each fires **only after `store.save()` resolves** (D-10), **never on button press** — we confirm the outcome, not the intent.

| Interaction | JS call | Semantic | Triggered from | Source |
|-------------|---------|----------|---------------|--------|
| Add todo | `impactFeedback("medium")` | Creation — single thunk | `useTodos.addTodo` after `save()` | D-10 |
| Toggle complete | `selectionFeedback()` | Binary state change — light tick | `useTodos.toggleTodo` after `save()` | D-11 |
| Delete todo | `notificationFeedback("warning")` | Destruction — multi-pulse | `useTodos.deleteTodo` after `save()` | D-12 |

**Guardrails:**
- Wrapped in `src/lib/haptics.ts` (three named functions: `hapticAdd`, `hapticToggle`, `hapticDelete`) — never called inline from a component.
- `isTauriRuntime()` guard short-circuits to no-op on web/desktop dev (D-14).
- Every plugin call inside `try/catch` that swallows errors — CRUD must never fail because haptics did (D-13, Pitfall 2).
- Called as `void hapticX()` (fire-and-forget) so haptic latency (50-150ms) never serializes into the UX path.

### Focus behavior

Existing Phase 2 pattern unchanged:
- Input: `focus:outline-none focus:ring-2 focus:ring-blue-700` — removes the native dotted outline, replaces with a branded 2px ring in accent blue. Accessible focus indicator, respects reduced-motion (static ring, no animation).
- Buttons: rely on native focus plus `active:opacity-90` feedback. No explicit focus ring needed since every button has a distinct filled or outlined surface.

### Disabled behavior

Existing Phase 2 pattern unchanged:
- Add button: `disabled:opacity-50` when input is empty or hook state is not `ready`.
- No disabled state on toggle or delete — rows are only rendered once state is `ready`.

| Element | Copy | Source file |

| Input placeholder | `Add a todo...` | `todo-input.tsx` |
| Primary CTA (add button label) | `Add` | `todo-input.tsx` |
| Loading state | `Loading...` | `todo-list.tsx` |
| Error state | `Could not load todos. Restart the app and try again.` | `todo-list.tsx` |
| Empty state heading | `No todos yet` | `todo-list.tsx` |
| Empty state body | `Add your first todo above` | `todo-list.tsx` |
| Toggle aria-label (incomplete → complete) | `Mark as complete` | `todo-item.tsx` |
| Toggle aria-label (complete → incomplete) | `Mark as incomplete` | `todo-item.tsx` |
| Delete aria-label | `Delete todo` | `todo-item.tsx` |
| Delete confirmation (destructive action) | **none** — delete is immediate, no confirm dialog | see rationale below |

### Destructive action: delete todo

**No confirmation dialog.** The plan ships immediate delete for these specific reasons:

1. **Scope:** CONTEXT "Deferred Ideas" defers swipe-to-delete and related gesture polish to v2. A confirm dialog would be a net-new UX surface beyond phase scope.
2. **Feedback substitutes for confirmation:** The `active:text-red-600` color flash + `notificationFeedback("warning")` multi-pulse haptic gives the user two simultaneous signals (visual + tactile) that a destructive action just happened. This matches native Android lists where delete is immediate with strong feedback.
3. **Data survivability:** Deleted todos are fully gone (no undo). This is acceptable because (a) CLAUDE.md notes this is a self-contained experiment with no critical data, and (b) re-adding a deleted todo is a single tap + text entry.

If post-phase device testing shows users deleting accidentally, revisit with undo toast or swipe-to-delete in v2 (ENH-01).

## Accessibility Contract

| Concern | Standard | Enforcement in this phase |
|---------|----------|---------------------------|
| Touch target minimum | 44×44 CSS px (Apple HIG) / 48dp (Material) | Phase 3 growing all four interactive controls to exactly `w-11 h-11` = 44×44 CSS px; 44px satisfies both standards given Android's density-independent mapping |
| aria-labels on icon-only buttons | WCAG 4.1.2 | Already in place on toggle (`Mark as complete` / `Mark as incomplete`) and delete (`Delete todo`). Re-verify after refactor |
| Focus indicator on keyboard nav | WCAG 2.4.7 | Input has visible `focus:ring-2 focus:ring-blue-700`; native focus on buttons preserved |
| Color-only state signaling | WCAG 1.4.1 | Completed state uses `line-through` text decoration + filled toggle + color change — three redundant signals, not color alone |
| Motion | WCAG 2.3.3 | No motion/animation introduced this phase. `active:opacity-90` is instantaneous, not an animated transition |
| Screen reader parity | WCAG 4.1.2 | Haptic is additive feedback, not the primary signal — visual state change + aria-labels remain canonical for assistive tech |
